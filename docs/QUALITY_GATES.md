# 検証の範囲

## 必要な工程

変更範囲を決める → ビルド・自動試験 → 実装と別コンテキストでのレビュー → 指摘修正 → 影響する試験の再実行、の順に進める。未実行・失敗・未確認を合格扱いしない。

## 試験の分類

| 分類 | 内容・判定方法 |
|---|---|
| 静的確認 | 差分、秘密情報・個人情報、依存版、文書と実装の整合を確認 |
| ビルド | Windowsで固定SDK・固定依存関係を使いReleaseビルド |
| 自動試験 | `TaskAssist.Tests` の実行結果JSONで件数と失敗数を確認 |
| Windows画面 | 架空データの試験ホストで操作して別途記録 |
| 実Outlook | 起動済みCOMのVersion取得、実メール読取り・原本不変、外部作用を分ける。Version取得だけで全連携合格にしない |
| 利用者受入 | 実際の使い心地の確認。自動試験件数から推定しない |
| 公開物確認 | ソースZIPの全エントリーとファイル内容、Git対象を確認 |

自動試験の識別子には過去の要件番号を含む。例えば `T070-subset` は部分的な試験であり、その要件全体の合格を意味しない。件数は当該ビルドの結果JSONで確認する。件数だけで全機能の網羅を主張しない。

## 主要な手動確認項目

- 初回の所属作成、担当一覧の保存、再起動後の保持。
- 架空の9月21日受付・10月31日期限が両月に表示されること。
- 担当ごとの依頼・回答・確認と、日付・回答・補足の保持。
- 存在しない日付の保存が拒否されること。
- 異動判断が不足すると進めず、異動後は空の所属になり、旧記録を閲覧できること。
- 文字サイズ変更時の操作性、表示が狭い画面での操作性。
- バックアップと復元、保存先に書き込めない場合の表示。
- Outlook対象の切替中・停止中の古い応答拒否、未取得の範囲が未確認と分かること。
- 新着の日付候補が注意に反映され、今の作業や入力フォーカスを勝手に変えないこと。
- 結果不明の送信・添付を自動再実行せず、本人確認へ回すこと。

## 未確認を残す項目

別のクリーンなPC、すべての表示倍率と画面寸法、実メール全経路、実業務での継続利用、最新コミットのGitHub Actionsは、実行記録が得られるまで未確認とする。AIの別コンテキストによるレビューと、人間による独立監査を区別する。
